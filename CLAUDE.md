# ঋ - Reé — project context

Marketing site and shop for **ঋ - Reé**, an independent clothing label shaped in Bengal ("Not everything old belongs in the past"). Products and orders live in **Supabase** and are managed in the admin at `/backroom` (see **Backend and backroom**); everything else (copy, collections, journal, the story pages' chapters) is hard-coded in the components and `src/data/`.

## Commands

- `npm run dev` — dev server (the user usually runs it themselves; check `lsof -iTCP -sTCP:LISTEN` before starting another — Next refuses a second dev server for the same directory. :3000 is often held by an unrelated API of the user's, so this project lands on :3001; `curl` the port for the `ঋ - Reé` title before trusting it)
- `npm run build` — production build; the cleanest way to verify a change
- `npm run lint` / `npx tsc --noEmit`

No test suite exists.

## Stack

- Next.js 16.3 (App Router, Turbopack), React 19.2, TypeScript strict
- Tailwind CSS v4 via `@tailwindcss/postcss` (no `tailwind.config`; theme lives in CSS `@theme`)
- `motion` 13 (Framer Motion's current package; import from `motion/react`) — used by `story-tiles.tsx` and the product pages; the landing page itself stays a server component
- `lucide-react` 1.x — **has no brand icons** (Instagram, Facebook, etc.); draw those as inline SVG
- Fonts through `next/font/google` only

## Backend and backroom

- **Supabase** (Postgres + Storage; project ref `ooxivccdgdfffcdbsxax`, region ap-northeast-1), reached **only from the server** with the secret key: `src/lib/supabase.ts` (`supabase()`, `supabaseConfigured()`, row types, `photoUrl` / `photoPath`). Env names are in `.env.example`: `SUPABASE_URL`, `SUPABASE_SECRET_KEY` (or legacy `SUPABASE_SERVICE_ROLE_KEY`), `AUTH_SECRET`, and `DB_PASSWORD` / `DB_HOST` / `DB_USER` for the scripts. `DB_NAME` in `.env` is the project's name, not the database's (that is always `postgres`).
- **Migrations and seed:** `npm run db:migrate` (`scripts/db.mts`, run by tsx with `--env-file=.env`) applies `supabase/migrations/*.sql` in order over a direct Postgres connection, each once (recorded in `ree_private.migrations`), each in a transaction; add a new file for a schema change, never edit an applied one. `npm run db:seed` fills empty `products` / `collections` / `hero_slides` tables from the starter data (filing products into collections by category) and creates the `SEED_ADMIN_EMAIL` account if it doesn't exist; it **never changes an existing account** unless run with `-- --reset-password`. `npm run db:images` uploads every image a row points at in `public/` (a `/…` path) into the bucket in its place (`hero/`, `<product slug>/`, `collections/<slug>[/<season>]/`) and repoints the row; hotlinked photos are left alone (they are other labels' photographs: link to them, never copy them). It has been run: the four hero slides are served from `ree-products/hero/` (the files stay in `public/landing/` for the starter fallback). (An earlier version reset the password whenever the variables were set; the user keeps `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD` in `.env`, so a routine seed reset it once and signed them out.) The direct `db.<ref>.supabase.co` host is IPv6-only and this machine has no IPv6, so `.env` points `DB_HOST` / `DB_USER` at the session pooler (`aws-1-ap-northeast-1.pooler.supabase.com`, `postgres.<ref>`). The script is `.mts` because package.json is not `"type": "module"` and it uses top-level await. Both migrations and the seed have been run (Nov 2026).
- **Schema:** `20261117000000_backroom.sql`: `products`, `orders` (numbers `REE-1001`…), `order_items` (a copy of name / size / price at order time), RLS on with no policies (anon key reaches nothing), the public `ree-products` photo bucket, and two `security definer` functions callable only by `service_role`: `place_order()` (prices from the table, tracked stock checked and taken, delivery fee, one transaction; raises `EMPTY_BAG` / `UNAVAILABLE` / `BAD_SIZE` / `SOLD_OUT`) and `set_order_status()` (cancelling restocks; cancelled is final). Change the schema with a new migration file, not by editing this one.
- **Fallback:** until Supabase is configured the shop reads the starter catalogue in `src/data/products.ts`, checkout answers `offline` (the preview letter, "nothing was sent"), and the backroom is a read-only preview. Don't remove the fallback; the build and local work rely on it.
- **Catalogue:** `src/lib/catalog.ts` (`getCatalog()`, `getCatalogProduct()`) is the storefront's only product source: published rows with at least one photo, mapped to `Product` by `rowToProduct`, which re-attaches what the table doesn't hold from the starter file (a story page's `story` by slug, a photo's tee `cutout` by URL). `productsFor` / `relatedTo` / `collectionProducts` take the list as an argument. **No data API for the browser** (the user asked for everything server-rendered): the bag in the header, /cart and /checkout get the catalogue with the page. `CatalogScope` (`catalog-scope.tsx`, async server component) wraps `LandingMain`, `SitePage` and the product route and hands `getCatalogEntries()` (only slug, old slugs, kind, name, category, price, colour and two photos: `CatalogEntry` in `products.ts`) to `CatalogProvider`; `useCatalog()` (`catalog-client.tsx`) reads it from context. `/api/catalog` is gone. `SitePage` lives in `site-frame.tsx`, apart from `site-page.tsx`, because the cart and checkout (client components) import `site-page.tsx` and a server-only import there breaks them (it did: /cart returned 500). The only browser-to-server calls left are mutations: server actions (checkout, the backroom) and the direct photo uploads. Listing and product pages are static; every backroom save calls `revalidatePath("/", "layout")`, and a placed order revalidates its products' pages (stock). `/products/[slug]` has `dynamicParams = true` so newly published pieces render on first visit.
- **Collections and seasons** (the user's model: a collection is a line such as "Nogor"; a season is one drop of it, S-1, S-2…; e.g. the DHAKA tee is Nogor S-1): migration `20261118000000_collections_seasons_banners.sql` adds `collections` (slug, name, tagline, blurb, `banner` photo, status, sort_order), `seasons` (collection, `number`, optional `name`, slug unique per collection, copy, banner, `starts_on` / `ends_on` shown on the page only, status), and `products.collection_id` / `season_id`; a trigger keeps a product's collection equal to its season's. The shop: `getCollections()` / `getCollection()` in `catalog.ts` (published collections with their published seasons; products get `collection` / `season` slugs and only link to published ones), `collectionProducts` / `seasonProducts` / `seasonLabel` in `collections.ts`, the landing page's collection tabs (`LandingMain` is async for this), a banner patch (`PageBanner`) at the top of a collection's or season's page, the collection page grouped by season with "More from …" for pieces without one, and the season page with chips for its sibling seasons. Stored photos keep their old `<slug>/` folder, which is harmless; old order items keep the slug they were ordered under and their links redirect.

## Splash screen — `src/components/splash-screen.tsx`

- The user asked for a splash with the logo only, after cookspace.co's (its CSS was read for the choreography; none of its assets are used). Rendered first in the root layout's `<body>`: a full screen in the logo's colours (emerald with the cream logo for the dark theme, the default; cream with the emerald logo for light, from the saved `ree-theme`) where the mark's three shapes draw their outlines one after another (`pathLength="1"` dashes, `--draw-delay`), fill while the outlines fade, REÉ rises in under it, the two settle together, and the screen fades at 3.8 s. Timing is `.ree-splash` at the bottom of `globals.css`; the script's 4.4 s timeout must stay in step with the exit.
- The inline script before it decides before first paint: every full load of `/` and `/landing` plays it (the user asked for /landing too); any other page only as the first page of a visit (`sessionStorage` `ree-splash`); the backroom never. Otherwise it sets `data-splash-done` at once and the splash is never painted. Navigating inside the site keeps the root layout, so it does not replay. `<html>` has `suppressHydrationWarning` for the `data-splash-*` attributes.
- While it plays (`data-splash-run` without `data-splash-done`) every other CSS animation on the page is paused, so the landing's entrance, the hero slideshow and the coming-soon gate start as it lifts. JS timers are not paused (none drive an entrance on load today). Without JavaScript nothing is held and the splash still fades by itself. Reduced motion: the finished logo, then a short fade.
- Checking it headless: time captures from the splash's own animation clock (`document.getAnimations()`, `ree-splash-exit`), not from `Page.navigate`; the dev server can take seconds to answer, and frames timed from the request looked like a splash that was already leaving.

## The two page experiences

### `src/components/silk-theme-transition.ts` — the theme-change sweep
- Toggling the theme sweeps a sheet of silk from the top-right corner to the bottom-left; the new theme is revealed under the cloth's opaque centre. The cloth wears the logo's colours (the user asked for this): silk in the logo's base, `#ffe7cc`, for → light and deep emerald satin (from the logo's `#00664f`) for → dark (`uTone`; `base` / `deep` / `spec` in the shader). The shader sits in a template literal, so its comments cannot contain backticks.
- The cloth is a **WebGL fragment shader, not an image**: a moving height field re-lit every frame, which is what makes it shiny and makes it wave. An earlier version stretched a 640px GIF across the screen and looked matte and choppy; don't go back to an image or video.
- One clock: the reveal is a WAAPI `clip-path` animation on `::view-transition-new(root)`, and each `requestAnimationFrame` reads that animation's eased progress (`effect.getComputedTiming().progress`) to place the cloth. Don't drive the seam with per-frame CSS custom properties on `<html>` — they are inherited, so every frame restyles the whole document.
- `.silk-veil` carries `view-transition-name: ree-silk` so it paints above the page snapshots; the rules are next to the dock styles in `globals.css`. All default view-transition animations are switched off there.
- `FRONT` / `BACK` / `OVERHANG` in the TS file size the cloth and its off-screen parking; `FRONT` and `BACK` are injected into the shader, and `OVERHANG` must cover the hem-wave amplitudes plus the shadow width if those change. The band `solid` in the shader must stay fully opaque around the seam (`a = 0`).
- One shared canvas/context for the page's lifetime (compiled at idle by `preloadSilkTransition`), capped at 1.6 MP. Fallbacks: no hardware WebGL or reduced motion → instant theme change; no View Transitions API → colours cross-fade while the cloth passes.
- To look at it without a browser window: Brave is installed, and `--headless=new --remote-debugging-port=…` plus CDP `Page.captureScreenshot` captures mid-transition frames (plain `--screenshot` hangs).

### Theming rules
- Landing: `[data-lp-theme="light"]` overrides the `--color-lp-*` tokens. Use tokens, not hex/black:
  - `text-lp-ink` for text on accent (yellow) fills — dark in both themes; `text-lp-bg` only on inverted `bg-lp-text` surfaces.
  - `bg-lp-card`, `bg-lp-deep`, `from-lp-deep-top` for cards and the footer band.
  - Overlays that fade into the page use `color-mix(in_oklab,var(--color-lp-bg)_N%,transparent)`.
- Coming soon: its palette is driven by `--ivory`, `--ivory-rgb`, `--ivory-muted`, `--ivory-bright`, `--stage-dark`, `--surface-rgb`, `--glass`, `--glass-hover-rgb`, `--gate-bg`, `--marker-glow`. Write new rules with those variables (e.g. `rgb(var(--ivory-rgb) / 40%)`) instead of literal colors, or light mode will break. Light mode also lightens the scene photo filter and `.scene-wash` so dark text stays readable over the imagery.

### Landing page motion
- Scroll effects are **CSS scroll-driven animations** (`animation-timeline: view()`) defined at the bottom of `globals.css`, so the page still needs no client JavaScript. They sit inside `@supports (animation-timeline: view())`; unsupported browsers (currently Firefox) just render the final state.
- Classes: `lp-enter` / `lp-enter-fade` (hero entrance on load, staggered with `--lp-delay`), `lp-reveal`, `lp-reveal-left`, `lp-reveal-right`, `lp-fade`, `lp-unveil` (image wipe), `lp-drift` / `lp-drift-x` (slow parallax for wordmarks and the style strip). Grids stagger with `--lp-stagger` (item index) rather than per-item delays, because scroll timelines ignore `animation-delay`.
- **Transform conflicts:** a keyframe animating `transform` overrides Tailwind positioning utilities like `-translate-x-1/2`, and because the animations are `both`-filled it never hands the property back. Use the opacity-only `lp-fade` / `lp-enter-fade` on elements centred that way, and keep `lp-unveil` on `clip-path` so the cards' `group-hover:scale-105` keeps working.
- **Stitches that sew themselves** (`vive-art.tsx`, the featured story's leaders): an SVG with `lp-sew` names a view timeline and every `.lp-sew-path` inside draws along it with the `pathLength="1"` dash trick (`--lp-sew-from` / `--lp-sew-to` on each path say where in the SVG's entry / cover it runs, so the order of sewing is set in the markup); `.lp-sew-fade` fades fills the same way. Dashed stitches are a solid path drawn through a dashed mask of itself (the mask needs explicit bounds, or a straight line has no mask area). `lp-float` is the one time-based loop (the tee swaying) and `lp-kantha` masks a layer into rows of running stitch for the featured story's background. The `.lp-sew` stitches now draw only the featured story's callout leaders.
- Every class is switched off under `prefers-reduced-motion: reduce`.

## Gotchas

- Scrollbars are hidden site-wide (`scrollbar-width: none` and `::-webkit-scrollbar` in the base layer; the user asked for it). Scrolling itself is unchanged.
- `globals.css` sets `body { overflow: hidden }` for the coming-soon stage. `LandingMain` therefore scrolls inside its own `h-svh overflow-y-auto` wrapper — in-page anchors depend on it.
- Element resets in `globals.css` live inside `@layer base`. Keep them there: unlayered rules outrank every Tailwind utility, which previously made `a { color: inherit }` silently override `text-*` on link-styled buttons and `svg { display: block }` override `hidden`.
- CSS Modules reject bare attribute selectors (`[data-x]`); scope under a class.
- The Tailwind dev process caches class candidates. If a build error references a class/asset no file contains anymore (e.g. `./assets/wordmark-texture.webp`), restart the dev server and delete `.next/dev`; `next build` will confirm the source is clean.
- `next/image` in Next 16 only allows `quality` values listed in `images.qualities` (default `[75]`); `next.config.ts` holds only `images.remotePatterns` for the hotlinked reference-store photographs (the featured story and `campaign-images.ts`).
- Tailwind only sees complete class strings — keep conditional classes as full literals (see `bricks[].place`, `journalPosts[].offset`).
- `tsconfig` path alias `@/*` maps to the repo root, not `src/`; existing code uses relative imports.
- Headless Brave captures (CDP `Page.captureScreenshot` after a programmatic `scrollTo`) do not advance scroll-driven timelines: every `animation-timeline: view()` effect reports a stale progress, so reveals and stitches look finished whatever the scroll position. To look at a mid-way state, set the property directly (for the stitches, `style.animation = "none"; style.strokeDashoffset = ".6"`) rather than trusting the capture; the real browser is fine.
